# HORIZON — Unity 3D World Bible

## 0. Mission

Build HORIZON as an engineering-grade software-in-the-loop visualization and experimentation environment for SIH26169.

The 3D world is not a game level and not a cinematic sci-fi scene. It is a controllable laboratory in which the user can understand, observe and stress the PAT loop.

Official PS basis: the system must provide a configurable virtual environment, moving beacon/target(s), movable virtual camera, automatic beacon detection/tracking, camera control, disturbances and real-time performance metrics.

## 1. Prime visual law

Every visible object must have a declared purpose. Each object must belong to at least one of:
1. simulation state;
2. sensor/optical representation;
3. technical explanation;
4. disturbance generation;
5. telemetry/diagnostics;
6. environmental legibility.

If an object exists only because it 'looks cool', remove it.

## 2. World abstraction

Do not invent an unsupported official mission scenario such as a specific satellite, aircraft, launch vehicle, military base or ISRO vehicle configuration.

Use a generic mobile terminal test scenario with configurable observer and target platforms. The visual scene should communicate relative motion and line-of-sight geometry without pretending to depict a specific real mission.

## 3. Core spatial objects

### 3.1 Observer platform
Purpose: provides a stable visual reference and carries the virtual camera.
Visual treatment: restrained aerospace test-platform geometry; no unnecessary mechanical detail.

### 3.2 Target platform
Purpose: carries the designated optical beacon and supplies target dynamics.
Visual treatment: compact mobile terminal platform; clearly not a photorealistic claim about a production ISRO terminal.

### 3.3 Designated beacon
Purpose: the perception target.
Outside sensor view: small physically motivated optical source.
Inside sensor view: synthetic optical spot generated by the sensor model.
Never use a giant neon sphere.

### 3.4 Virtual camera boresight
Purpose: shows the direction the simulated camera is pointing.
Representation: a subtle ray/cone or frustum.
Only visible in engineering/observer/diagnostic modes.

### 3.5 Camera FOV volume
Purpose: makes acquisition/tracking geometry understandable.
Representation: transparent frustum/cone with restrained opacity.
It must update with the real camera parameters.

### 3.6 Line of sight (LOS)
Purpose: explains geometric relationship between camera and beacon.
Shown when diagnostic overlays are enabled.
Must originate from actual camera pose and terminate at actual target position.

## 4. Camera/view hierarchy

### View A — Observer View
Purpose: explain the system spatially.
Shows target, observer, FOV, LOS and trajectories.

### View B — Sensor View
Purpose: represent what the virtual optical camera receives.
Shows synthetic image and only the overlays enabled by the user.

### View C — Diagnostic View
Purpose: expose geometry and estimation.
Shows angular error, predicted state, covariance/uncertainty, measured point and camera center.

The PAT algorithm itself must operate on the virtual sensor, not on the observer camera used for presentation.

## 5. Environmental composition

Use a sparse, legible environment:
- atmospheric volume/haze when justified by the current disturbance configuration;
- distant terrain or neutral background reference to establish depth;
- restrained clouds only if they help explain visibility/background conditions;
- no decorative city, military base, launchpad, random spacecraft, satellites, planets or stars unless a concrete simulation purpose is documented.

The background should be visually quiet so the beacon, FOV, trajectories and telemetry remain legible.

## 6. Optical signal visualization

Beacon rendering pipeline:
source intensity → simplified spatial spread/PSF → background → sensor noise → optional motion blur/degradation.

The visual must remain consistent with the configured sensor model.

If the user increases noise, the image must become noisier because of the same parameter that the simulation logs.

If motion blur is increased, the sensor image must respond accordingly.

Do not create a fake visual effect that is disconnected from a simulation parameter.

## 7. Trajectory visualization

### Actual trajectory
Solid restrained line.
Source: scenario engine ground truth.

### Predicted trajectory
Dashed line.
Source: estimator output.

### Search trajectory
Visible only in SEARCH/ACQUIRE/REACQUIRE states.
Source: actual camera command history.

### Uncertainty region
Ellipse/cone derived from estimator covariance.
Never use an arbitrary decorative ellipse.

## 8. State-driven visual behavior

### SEARCH
Camera executes real acquisition policy.
Search path visible.
Status color: cyan.

### ACQUIRE
Candidate target evidence becomes visible.
Search area may narrow.
Status color: cyan.

### TRACK
Target remains near camera center.
Uncertainty visual contracts according to actual covariance.
Status color: green.

### DEGRADED
Target still tracked but confidence is reduced or disturbance is elevated.
Uncertainty expands according to actual estimator state.
Status color: amber.

### REACQUIRE
Target has been lost and a recovery policy is active.
Local search region/path visible.
Status color: red for loss event; recovery progress must not use red as decoration.

## 9. Disturbance visualization

Every disturbance must alter simulation state as well as appearance.

### Vibration
Affects camera/platform orientation through a defined disturbance model.
Visual: subtle motion only as large as the configured parameter warrants.

### Sensor noise
Affects measurement image or extracted observation.
Visual: sensor image degradation.

### Motion blur
Affects rendered sensor observation according to relative motion and exposure approximation.

### Signal fluctuation
Changes beacon intensity/measurement quality.

### Occlusion
Actually removes/attenuates beacon observability for a defined interval.

### False targets
Creates competing detections with their own positions and trajectories.

### Actuator latency
Changes control response timing; must not merely shake the camera visually.

## 10. Interaction philosophy

The judge should be able to change one parameter and understand its consequence.

Example:
Target acceleration ↑ → target trajectory changes → estimator prediction changes → camera command changes → tracking error changes → metric updates.

The system must never present controls that are visually disconnected from the underlying model.

## 11. Lighting

Lighting is for legibility and depth, not spectacle.

Use:
- soft directional/key lighting;
- controlled ambient/fill;
- subtle atmospheric separation;
- limited bloom only where it reinforces the optical-source representation.

Avoid:
- dramatic volumetric light shafts without a simulation reason;
- excessive bloom;
- neon rims on every object;
- pulsing lights for decoration;
- cinematic lens effects that hide the telemetry.

## 12. Materials

Materials should be low-complexity and technical:
- matte engineered surfaces;
- restrained metal accents;
- neutral platform materials;
- controlled emission only for beacon/sensor-related elements.

Do not create elaborate PBR environments that increase asset and performance cost without supporting the experiment.

## 13. Performance budget

The application must remain responsive on a realistic mid-range development/demo machine.

Do not trade simulation fidelity for decorative geometry.

The performance benchmark must measure algorithm/runtime behavior, not the frame rate of a visually overloaded scene.

Separate:
- visual presentation FPS;
- algorithm processing latency;
- simulation timestep.

Do not conflate them in reporting.

## 14. What must NEVER appear

Never add without explicit authorization:
- fake ISRO logos or mission patches;
- invented real mission names;
- fictional government telemetry presented as official;
- random rockets/spacecraft;
- laser beams presented as completed communication links;
- physical hardware claims that the PS does not require;
- fake benchmark numbers;
- decorative HUD widgets with no underlying data;
- AI-generated gibberish telemetry;
- impossible camera motion that ignores actuator dynamics.

## 15. What makes the world immersive

Immersion comes from coherence:

The camera moves because the controller commanded it.
The target moves because the scenario engine commanded it.
The image degrades because the disturbance engine changed it.
The uncertainty grows because the estimator became less certain.
The state graph changes because the mode manager changed state.
The benchmark numbers change because the underlying run changed.

The user should feel that the entire world is one coupled system.

## 16. Definition of success

A first-time viewer should be able to understand the loop without verbal explanation:

unknown target → search → beacon detected → camera aligns → target moves → disturbance occurs → tracking degrades → target is lost → recovery search → target reacquired → quantitative proof.

That is the HORIZON experience.
